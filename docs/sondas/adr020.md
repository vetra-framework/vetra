# Sonda de revisão de autorização e entrega live

A [sonda do ADR-020](../../script/sonda_adr020.rb) verifica os mecanismos do PostgreSQL usados na proposta
de revisão por tenant e demonstra uma decisão de entrega strict. O [ADR-030](../adr/030-tenants-da-revisao-de-autorizacao.md)
resolve a origem do tenant nos triggers de instrução. O gerador e o runtime live continuam pendentes.

## Executar

Use Ruby 4.0.9, PostgreSQL 17 ou 18 e um banco descartável. A sonda carrega `pg` e `json` por `bundler/inline`:

```sh
DATABASE_URL=postgres://superusuario@127.0.0.1:5432/descartavel ruby script/sonda_adr020.rb
```

A conexão inicial precisa de superusuário para criar e assumir os papéis exclusivos do teste. O proprietário
das tabelas e funções é um papel `NOLOGIN NOSUPERUSER NOBYPASSRLS`. As sessões de aplicação usam outro papel,
também sem superusuário ou `BYPASSRLS`, com acesso somente aos objetos necessários. Esses papéis são fixtures;
não são os papéis de produção nem uma implementação do contexto assinado e do RLS.

O schema e os papéis `vetra_sonda_adr020_*` são exclusivos por execução. As sessões são fechadas por caso e
os objetos são removidos no `ensure`. A saída é 0 quando todas as verificações passam, e 1 quando há falha.
A [CI](../../.github/workflows/ci.yml) executa a sonda no PostgreSQL 17 e 18, separada dos testes do compilador.

## Verificações

| Caso | Resultado exigido |
|---|---|
| Inserção de 200 vínculos em lote, sem contexto | Uma revisão por tenant afetado, sem consultar seletor de sessão |
| Atualização e exclusão | Somente os tenants das linhas alteradas têm a revisão incrementada |
| Instruções que afetam zero linhas | Nenhuma revisão é criada |
| Mudança de tenant | Origem e destino são invalidados, mesmo com um seletor de sessão diferente |
| Commit e rollback | Permissão, revisão e notificação confirmam ou desfazem juntas |
| Escritas concorrentes | O servidor confirma a espera por lock; os dois incrementos permanecem |
| Privilégios da aplicação | Escrita direta nas revisões/outbox, `TRUNCATE` e desativação de triggers são recusados |
| Objetos temporários | Não substituem a tabela de revisões nem as relações de transição |
| Revogação strict sem receber invalidação | A assinatura afetada deixa de ser elegível para entrega e a outra permanece autorizada |
| Revisão indisponível ou ausente | A demonstração suspende a entrega; após recuperar a consulta, reautoriza antes de permitir dados |
| Snapshot antigo | A demonstração recusa `REPEATABLE READ`; uma consulta nova observa a revogação |
| SQL direto sobre mensagem | Versão e evento mudam atomicamente; `OLD`/`NEW` incluem somente os campos permitidos pela fixture |
| Releitura agrupada | 200 assinantes de demonstração formam quatro grupos, separados por tenant e predicado, com quatro consultas |

Os triggers usam `OLD TABLE` e `NEW TABLE` para descobrir os tenants, e `INSERT ... ON CONFLICT DO UPDATE`
para incrementar a revisão. As esperas concorrentes são confirmadas por `pg_blocking_pids`; o relógio
somente limita a espera. A suspensão após falha é exercitada com um lock real na tabela de revisões e
`lock_timeout`, cuja recusa é confirmada pelo SQLSTATE `55P03`.

O verificador strict lê a revisão antes de cada decisão de lote e reconsulta o vínculo quando a revisão
muda. Ele não depende de receber `NOTIFY`. Não altera a janela residual do ADR-020: um lote cuja leitura de
revisão começou antes do commit da revogação pode terminar depois. Não há teste de entrega por rede aqui.

## Medição de 2026-11-03

No WSL, com Ruby 4.0.9, `pg` 1.7.0 e PostgreSQL 18.6, as **13 verificações passaram**. O servidor usou um
diretório temporário e socket Unix exclusivo, sem escuta TCP, e foi encerrado no fim. Uma consulta aos
catálogos confirmou que nenhum schema ou papel da sonda permaneceu após o sucesso.

Foram introduzidas quatro falhas em cópias temporárias, todas detectadas com saída 1:

| Falha introduzida | Verificações que passaram |
|---|---|
| Manter a revisão anterior no conflito do UPSERT | 9/13; também permitiu reproduzir uma decisão de entrega após revogação |
| Permitir entrega quando a consulta de revisão falha | 12/13 |
| Retirar a recusa de snapshot antigo | 12/13 |
| Colocar todos os campos de `NEW` no evento | 12/13; o conteúdo pessoal apareceu no evento |

A limpeza removeu o schema e os papéis também em cada execução com falha.

## Limites

As funções SQL e a lista de campos dos eventos são escritas para a fixture; não são geradas da IR. A
classificação pessoal de `body` é fixa nesta demonstração. O agrupamento e o predicado de autoria são
explícitos no script; não há compilação de templates ou avaliadores a partir das políticas. As quatro
consultas demonstram o caminho agrupado da fixture, sem medir o custo de produção.

A autorização consulta vínculos com filtros SQL explícitos. Não há identidade autenticada, contexto
assinado, RLS, autenticação da assinatura, auditoria, transporte, revogação de delegações ou garantia de
isolamento contra código comprometido. Os fixtures de assinatura são estados internos da demonstração,
sem uma API de runtime. O modo `balanced` e seus intervalos não foram implementados.

Não foram exercitados múltiplos processos de aplicação, indisponibilidade real do servidor, carga,
deadlocks entre várias instruções, tabelas particionadas, cascatas ou combinações de eventos de UPSERT.
Aplicações sem tenant precisam de uma chave de revisão própria. Os eventos de exclusão de mensagens,
o provisionamento inicial das revisões, retenção, failover e ressincronização continuam pendentes.
Os **12 critérios do ADR-020 e o gate G4 seguem
dependendo da implementação integrada**, com os papéis de produção.

O ADR aceito preserva o texto da data de aceite; este relatório registra a evidência posterior.
